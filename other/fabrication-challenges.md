This document records the main problems we faced while building the robot and the
engineering decisions taken to solve them.

---

## 🔴 First version — Raspberry Pi

Our first prototype used a **Raspberry Pi** as the main controller. Two major
problems made this approach impractical for the competition.

> [!WARNING]
> **Problem 1 — Complex setup & installation**
> Getting the Raspberry Pi ready required a full desktop workflow — an **external
> keyboard, monitor and mouse** — just to install the dependencies and configure
> the system. Every bring-up was slow and hard to reproduce, a serious drawback
> for a competition robot that must be set up quickly and reliably.

> [!CAUTION]
> **Problem 2 — Servo calibration on the PWM pin**
> The **frequency of the PWM pulses** generated by the Pi did **not match the
> steering servo's required configuration**, so the servo could not be positioned
> accurately or repeatably. Precise steering — essential for Future Engineers —
> was impossible to achieve on this platform.

---

## 🟢 Decision — switch to the Arduino UNO Q

Because of these problems, the team moved to the **Arduino UNO Q**. It offers a
**framework similar** to the Raspberry Pi, since it can run **both Python and
C/C++ code** on the same board — so we **ported the Python code from the Pi to the
UNO Q** and split the responsibilities between the two sides of the board:

| Layer | Language | Responsibility |
|-------|:--------:|----------------|
| 🧩 **MCU side** | **C / C++** | Controls the **servo motor** and the **DC drive motor** (reliable, hardware-timed PWM) |
| 🐍 **Linux side** | **Python** | Controls the **camera** and handles all the information gathered from the **motors and the camera** |

> [!TIP]
> **Why this solved the problems**
> - The UNO Q's **microcontroller** generates the PWM in hardware at the correct
>   frequency → **fixed the servo-calibration problem**.
> - The **Linux side** still runs **Python** for the camera and high-level logic →
>   we kept the Raspberry Pi code that already worked.
> - Bring-up became much simpler — **no dedicated keyboard, monitor and mouse**.

---

## 🎛️ Calibrating the servo with an HTML web UI

When we moved to the Arduino UNO Q, the steering servo still had to be calibrated.
The servo had been **detached from the first (Raspberry Pi) version**, so once it
was remounted its real orientation was **unknown**.

> [!IMPORTANT]
> On the **first try** the control asked the servo for an angle of **−52°**, but a
> standard servo only accepts **0°–180°**. The command was out of range, so the
> servo could not reach the requested position.

To fix this we built a small **web control (HTML Web UI)** that drives the servo
through the **Arduino UNO Q's internal protocol** (RouterBridge RPC). The page
([`src/assets/index.html`](../src/assets/index.html)) shows a **slider** that lets
us sweep the servo across its range and read back the angle that is actually
applied — so we could find the true limits and the real centre **by measuring,
instead of guessing**.

### 📐 Calibration results

| Measurement | Result |
|-------------|:------:|
| Orientation error vs. expected | **~270° off** |
| Calibrated **centre** (straight-ahead) | **79°** |

These measured values are now used as the reference angles for steering in the
control code.
