# Fabrication challenges & lessons learned

This document records the main problems the team faced while building the robot,
and the engineering decisions taken to solve them.

---

## First version — Raspberry Pi

Our first prototype used a **Raspberry Pi** as the main controller. Two major
problems made this approach impractical for the competition.

### 1. Complex setup & installation

Getting the Raspberry Pi ready required a full desktop workflow — an **external
keyboard, monitor and mouse** — just to install the dependencies and configure the
system. This made every bring-up slow and hard to reproduce, which is a serious
drawback for a competition robot that must be set up quickly and reliably.

### 2. Servo calibration on the PWM pin

The most critical issue was calibrating the **steering servo** on the Raspberry
Pi's **PWM pin**. The **frequency of the pulses** generated by the Pi did **not
match the servo motor's required configuration**, so the servo could not be
positioned accurately or repeatably. This made precise steering — essential for
the Future Engineers challenge — impossible to achieve on this platform.

---

## Decision: switch to the Arduino UNO Q

Because of these problems, the team decided to move to the **Arduino UNO Q**. It
offers a **similar framework** to the Raspberry Pi, since it can run **both Python
and C/C++ code** on the same board. This let us reuse our existing work: we
**ported the Python code from the Raspberry Pi to the UNO Q** and split the
responsibilities between the two sides of the board.

| Layer | Language | Responsibility |
|-------|----------|----------------|
| **MCU side** | **C / C++** | Controls the **servo motor** and the **DC drive motor** (reliable, hardware-timed PWM) |
| **Linux side** | **Python** | Controls the **camera** and handles all the information gathered from the **motors and the camera** |

### Why this solved the problems

- The UNO Q's **microcontroller** generates the servo/motor PWM in hardware with
  the correct frequency, which **fixed the servo-calibration problem** we had on
  the Raspberry Pi.
- The **Linux side** still runs **Python** for the camera and high-level logic, so
  we kept the parts of our Raspberry Pi code that already worked.
- Setup became much simpler — no dedicated keyboard, monitor and mouse needed to
  bring the robot up.
